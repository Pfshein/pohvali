## 1. Решение

В авторизованном Telegram Mini App одновременно существуют два интерфейса:

- `classic` — текущий экран без визуальных и поведенческих изменений;
- `room` — новый почти полноэкранный домашний экран по утверждённому макету.

Пользователь вручную переключается между ними. Переключение не меняет backend,
схему БД, API, Telegram-аутентификацию, ключ шифрования, похвалы, баланс, календарь,
маскота или настройки напоминаний. Новый UI является альтернативным представлением
тех же данных и команд.

Начальный режим для существующих и новых пользователей — `classic`, пока пользователь
сам не выберет `room`. Выбор хранится только локально под версионированным ключом
`pohvala.ui-mode.v1`. Неизвестное или повреждённое значение означает `classic`.
Удаление ключа полностью отключает эффект настройки.

## 2. Почему изменение обратимо

```text
SessionRoot (Telegram auth, crypto, API adapters)
  └─ App (единое бизнес-состояние и команды)
      ├─ ClassicAppView  ← существующий UI
      └─ RoomAppView     ← новый UI, загружается лениво
          ├─ RoomHome (DOM HUD и композиция)
          ├─ RoomCanvas (Pixi lifecycle bridge)
          └─ sheets (существующие функции в новом контейнере)
```

Запрещено:

- менять `SessionRoot` так, чтобы браузер мог обойти Telegram bootstrap;
- вводить query-параметр, который открывает фиктивный `App` в production;
- менять контракты API или таблицы БД ради UI;
- переносить текст похвал или ключ шифрования в Pixi/RoomState;
- удалять classic-компоненты до отдельного продуктового решения;
- использовать сам мокап целиком как фон с нарисованными неинтерактивными кнопками.

Откат состоит из удаления ветки `room`, ленивого импорта и локального ключа. Старый
UI при этом уже находится в production-коде и остаётся рабочим на каждом этапе.

## 3. Экран Room UI v2

### 3.1. Контейнер

- Экран занимает `100dvh`, ширина ограничена текущими `320…560px`.
- На телефоне нет внешней карточки и общего page scroll: комната — основной viewport.
- Учитываются `env(safe-area-inset-top)` и `env(safe-area-inset-bottom)`.
- Фон тёплый персиково-кремовый, с очень слабой бумажной фактурой, без заметного
  паттерна и без цветной вуали поверх маскота.
- Верхняя часть — стена; нижняя — светлый деревянный пол. Граница пола проходит
  примерно на 55–58% высоты контентной области.
- В desktop preview экран центрируется в колонке до 560px; рамка iPhone из мокапа
  не воспроизводится.

### 3.2. Композиция сверху вниз

1. Верхний HUD: слева спокойная плашка прогресса, справа круглая кнопка настроек.
2. Большая зона воздуха.
3. Реплика маскота над центральной сценой.
4. Активный маскот, визуально сидящий в базовом кресле.
5. Слева над навигацией — «Обустроить»; справа — спокойная подпись.
6. Нижняя навигация: календарь, выступающая центральная кнопка похвалы, профиль.

При высоте 780–900 CSS px композиция помещается без прокрутки. При высоте меньше
680px уменьшаются вертикальные промежутки и центральная сцена, но HUD, CTA и все
три пункта навигации остаются видимыми и кликабельными.

### 3.3. Верхний HUD

**Прогресс:** форма и положение соответствуют плашке «1 день подряд» на мокапе,
но streak запрещён `docs/product-brief.md`. Видимый текст:

- `0` отмеченных дней текущего месяца: «Сегодня можно начать»;
- `1`: «1 день заботы о себе»;
- `2–4`: «N дня заботы о себе»;
- остальные значения: «N дней заботы о себе».

Число вычисляется из уже загруженного `markedDays`; новых endpoint'ов нет. Ведущий
значок — тёплое сердце/искра, а не огонь. `aria-label` уточняет: «В этом месяце: …».

**Настройки:** круглая DOM-кнопка не меньше 48×48px с качественным outline SVG.
Открывает `SettingsSheet`. Внутри находится действие «Вернуться к старому дизайну».
Это основной обратный переключатель; отдельной постоянной кнопки поверх комнаты нет.

### 3.4. Реплика

Точный видимый текст: «За что ты хочешь похвалить себя сегодня?»

- Две строки на ширине 360–430px.
- Светлая полупрозрачная speech bubble с небольшим хвостиком вниз.
- Маленькое сердце находится в круглом выступе по центру верхнего края.
- Текст остаётся DOM-текстом, а не частью canvas или изображения.

### 3.5. Центральная сцена

- Центр экрана занимает активный маскот из фактического `MascotCollection`.
- Нельзя hardcode'ить выдру с мокапа или список только из starter-маскотов.
- `assetPath`, `code` и `name` берутся из ответа коллекции; при временной ошибке
  применяется существующий локальный fallback, не падение всего App.
- Базовое кресло — отдельный зарегистрированный ассет. Для корректного перекрытия
  разрешены два экземпляра: `chair.basic.back` на слое `furniture` и
  `chair.basic.front` на слое `foreground`; маскот остаётся на слое `mascot`.
- Все три элемента создаются через `instantiateRoomItem`, а не вручную внутри
  renderer. У них фиксированные instance id и общая стартовая точка.
- В первом релизе базовая композиция закреплена. Свободное перемещение составного
  кресла не вводится без отдельной модели группировки.
- Для маскота используется прозрачный PNG/WebP. Если специальной seated-позы нет,
  применяется `object-fit: contain`/Pixi scale и визуально проверенное смещение над
  сиденьем. Новые admin-маскоты обязаны иметь безопасный fallback-компоновщик.

Перед реализацией нужен отдельный art pass: создать чистые прозрачные ассеты кресла
в принятой оливковой стилистике и, если необходимо, его front/back части. Грубое
процедурное фиолетовое кресло из текущего прототипа в финальный UI не входит.

### 3.6. Нижняя зона

**«Обустроить»:** компактная pill-кнопка слева с outline-иконкой комнаты/кресла.
В первом этапе переключает `editing`. Текст становится «Готово». Интерактивные
предметы получают деликатный контур; базовый составной chair/mascot остаётся locked.
Кнопка имеет `aria-pressed`.

**Подпись справа:** «Твой уют начинается\nс малого шага 🌿». Декоративная, не кнопка.

**Bottom navigation:** светлая матовая поверхность высотой около 132px с мягким
вогнутым силуэтом вокруг центрального CTA. Реализуется CSS/DOM, не Pixi.

- слева: outline calendar + «Календарь»;
- центр: круглая оливковая кнопка 112–124px с белым сердцем и подписью
  «Похвалить себя»;
- справа: outline profile + «Профиль».

Все targets не меньше 48×48px. Центральная кнопка открывает существующий encrypted
composer. Calendar и Profile открывают modal bottom sheets поверх комнаты, поэтому
RoomHome не размонтируется и пользователь закрывает sheet обратно в комнату.

### 3.7. Sheets

Одновременно открыт максимум один overlay:

```ts
type RoomOverlay = "none" | "composer" | "calendar" | "profile" | "settings";
```

- `CalendarSheet` переиспользует `MonthCalendar` и текущую загрузку/чтение дня.
- `ProfileSheet` содержит коллекцию маскотов, reminders, recovery и privacy.
- `SettingsSheet` содержит быстрые настройки и «Вернуться к старому дизайну».
- Composer остаётся единственным существующим сценарием создания похвалы.
- Sheet имеет `role="dialog"`, доступное имя, close control, закрытие по Escape и
  scrim, focus trap и возврат фокуса на кнопку-источник.
- Telegram BackButton, если будет подключён позднее, закрывает overlay, но не нужен
  для первого релиза.

## 4. Design tokens

Цвета фиксируются после выборки финальных ассетов; стартовые значения для CSS:

| Token | Значение | Роль |
|---|---:|---|
| `--room-wall` | `#f6d3a2` | стена |
| `--room-floor` | `#e8bd82` | пол |
| `--room-surface` | `rgba(255, 239, 211, .82)` | HUD/sheets/nav |
| `--room-olive` | `#74754b` | основной CTA |
| `--room-olive-strong` | `#5f6238` | текст и active |
| `--room-amber` | `#eaa24d` | маленький акцент |
| `--room-cream` | `#fff3dc` | сердце/светлые элементы |
| `--room-shadow` | `0 14px 40px rgba(111, 78, 40, .14)` | мягкое поднятие |

- Font: существующий Nunito; новый шрифт не добавляется.
- Основной текст: 16–20px/1.35; nav labels: 14–16px; CTA: 15–17px/700.
- Радиусы: pill `999px`, HUD circle `50%`, sheet `28px 28px 0 0`.
- Border: 1px `rgba(112, 82, 48, .10)`.
- Иконки: outline, round cap/join, единая толщина 1.8–2px, `currentColor`.
- Motion: 180–240ms; при `prefers-reduced-motion` переходы практически отключены.

## 5. React/Pixi граница

React владеет:

- `uiMode`, `RoomOverlay`, `editing`;
- данными praise/calendar/profile/collection;
- текстом, кнопками, sheets, focus management;
- сериализуемым `RoomState` и выбором активного маскота.

Pixi владеет:

- canvas, display objects, texture lifecycle;
- сортировкой по слоям и визуальным resize;
- pointer-событиями разрешённых предметов;
- будущими idle/tween/particle effects.

Pixi не вызывает API, не открывает dialogs и не хранит продуктовые данные. Его
единственный исходящий сигнал первого этапа — подтверждённое перемещение экземпляра:

```ts
type RoomItemMoveHandler = (id: string, position: NormalizedPoint) => void;
```

Сохраняются существующие контракты `RoomItem`, normalized coordinates `0…1`, zones,
layer bases, versioned serialization и lifecycle `mount/update/resize/destroy`.

## 6. UI mode и состояние

```ts
export type UiMode = "classic" | "room";

export interface UiModePreferenceV1 {
  schemaVersion: 1;
  mode: UiMode;
}
```

- Pure parser отвергает неизвестные версии/режимы и возвращает `classic`.
- Adapter читает/пишет localStorage; ошибка storage не блокирует запуск.
- Переключение меняет UI немедленно, запись preference выполняется best effort.
- `RoomState` поднимается выше условного представления или RoomHome не размонтируется
  при overlay. Переключение `room → classic → room` не сбрасывает расстановку в
  рамках сессии.
- Постоянное сохранение расстановки относится к PH-903 и не смешивается с ключом UI.

## 7. Lazy loading и отказоустойчивость

- `RoomAppView` и весь PixiJS импортируются динамически только после выбора `room`.
- Classic initial bundle не должен удвоиться из-за PixiJS.
- Suspense fallback показывает «Открываем комнату…» и DOM-кнопку возврата.
- Error Boundary при ошибке chunk показывает «Не получилось открыть комнату» и
  «Вернуться в старый UI».
- Ошибка инициализации canvas не скрывает speech bubble, CTA и нижнюю навигацию.
- После возврата classic продолжает работать без reload.

## 8. Сценарии

### Переключение

1. Пользователь проходит обычные Telegram session/onboarding gates.
2. В classic нажимает «Новый дизайн».
3. App сохраняет `room`, лениво загружает UI и показывает комнату.
4. В Settings нажимает «Вернуться к старому дизайну».
5. App немедленно показывает неизменённый classic и сохраняет `classic`.

### Похвала

1. Пользователь нажимает центральное сердце.
2. Открывается существующий composer.
3. Сохранение использует текущий `onSubmitPraise`; шифрование и API не меняются.
4. После успеха обновляются balance/calendar и composer закрывается в комнату.

### Календарь и профиль

1. Нижняя кнопка открывает соответствующий sheet.
2. Все существующие loading/error/success состояния сохраняются.
3. Закрытие возвращает пользователя и фокус в RoomHome без пересоздания canvas.

## 9. Доступность

- Все продуктовые команды — настоящие DOM `button`, а не hit areas canvas.
- Canvas имеет `aria-hidden="true"`; смысловая сцена описана на RoomHome.
- Контраст текста/иконок не ниже WCAG AA для обычного текста.
- Focus ring заметен на тёплом фоне; порядок Tab соответствует визуальному порядку.
- Dynamic status использует `aria-live="polite"`, ошибки — `role="alert"`.
- Decorative icons имеют `aria-hidden`; кнопки имеют русские accessible names.
- Touch targets минимум 44×44px, для главной навигации — 48×48px.

## 10. Responsive и Telegram

- Проверяем ширины 320, 360, 390, 430 и 560px.
- Проверяем высоты 568, 667, 780, 844 и 932px.
- При появлении клавиатуры composer остаётся доступным и прокручиваемым.
- Используется `100dvh`, не только `100vh`; safe area не перекрывает nav.
- Telegram `ready()`/`expand()` остаются только в `main.tsx` через текущий client.
- Никаких production preview bypass. Локальный browser QA разрешён только через
  существующий mock mode или временный DEV-only entry, удаляемый до commit.

## 11. Ассеты

Обязательный manifest:

```ts
type RoomAsset =
  | { kind: "texture"; src: string }
  | { kind: "procedural"; renderer: "room-background" };
```

Планируемые файлы:

```text
frontend/public/assets/room/v2/chair-back.webp
frontend/public/assets/room/v2/chair-front.webp
frontend/public/assets/room/v2/texture.webp       # только если нужна, очень слабая
```

Требования: transparent WebP для chair частей, одинаковый canvas/crop/anchor,
без текста, без кнопок, без телефонной рамки, без встроенного маскота. Источник и
лицензия фиксируются рядом с manifest. При ошибке загрузки renderer показывает
спокойную нейтральную заглушку, но DOM UI остаётся работоспособным.

## 12. Что не входит

- backend persistence комнаты;
- серверный feature flag и A/B analytics;
- streak, штрафы, потеря прогресса, scarcity;
- магазин мебели и полноценный inventory;
- групповой drag составных объектов;
- сложные mascot animations, частицы, звук;
- замена/удаление classic UI;
- новая схема авторизации или браузерный production login.

## 13. Критерии приёмки

1. После Telegram auth classic открывается как раньше, пока пользователь не выбрал room.
2. «Новый дизайн» и «Вернуться к старому дизайну» переключают режимы без reload.
3. Выбор переживает повторное открытие; invalid preference безопасно даёт classic.
4. Ни API, ни БД, ни crypto/session contracts не изменены.
5. Room viewport воспроизводит структуру, иерархию, палитру и плотность мокапа.
6. Активный маскот приходит из фактической коллекции; admin asset не hardcode'ится.
7. Praise, Calendar, Profile, Settings и Furnish являются рабочими DOM-действиями.
8. Calendar/Profile/Settings открываются sheets и возвращают focus в RoomHome.
9. Переключение режимов и overlays не сбрасывает расстановку текущей сессии.
10. Pixi lifecycle освобождает listeners, textures/views и canvas при destroy.
11. Classic initial JS остаётся отдельным от Pixi chunk; build фиксирует размеры.
12. Ошибка lazy chunk/canvas оставляет доступный путь обратно и к похвале.
13. `npm run check` проходит полностью.
14. Browser QA пройден на 390×844 и коротком 360×667 viewport.
15. Финальный screenshot визуально сопоставлен с исходным мокапом минимум по пяти
    пунктам: композиция, палитра, типографика, центральный asset, bottom navigation.
