# Дизайн PH-405: admin-команда добавления маскота

**Дата:** 2026-09-02
**Статус:** утверждён для реализации

## Цель

Владелец проекта добавляет нового маскота из личного чата с ботом без
изменения кода, пересборки frontend и ручной правки БД. Команда:

```text
/add_mascot <code> <unlock_threshold> | <Имя> | <Описание>
```

PNG отправляется документом с этой подписью.

## Архитектура

Существующий webhook (`/telegram/{secret_path}`) остаётся единственной точкой
входа. Обработка `/add_mascot` следует паттерну `/start`: чистый парсер без
I/O в `app/modules/bot/add_mascot.py`, оркестрация в webhook-роутере, доставка
через существующий sender.

```text
webhook update (document + caption "/add_mascot …")
    -> parse_add_mascot(update, admin_ids)     # pure: auth, формат подписи
    -> downloader(file_id) -> bytes            # aiogram get_file/download_file
    -> validate_png(bytes)                     # pure: сигнатура, 1 MiB, 256–1024 px, alpha
    -> add_mascot(session, …)                  # одна транзакция, каскадная целостность
    -> AdminReply(chat_id, text, preview)      # отправка документом-превью
```

Ключевое решение по выдаче картинок: `asset_path` нового маскота сразу
заполняется как `/api/v1/mascots/{code}/image`. Фронтенд уже рендерит каталог
по `asset_path` из `GET /api/v1/mascots`, поэтому новый маскот появляется без
изменений фронтенда и без нового deploy. Эндпоинт изображения публичный, как и
статические ассеты сид-маскотов (это каталожные данные, не пользовательские);
`<img>` не умеет отправлять Telegram-заголовки.

## Хранение

Миграция добавляет nullable-колонку `image_data BYTEA` в `mascots` (только
админ-маскоты хранят байты; у сидов остаются файлы). В модели колонка
deferred — запросы каталога не тянут байты.

## Валидация

- Команда только в личном чате и только от Telegram ID из `TELEGRAM_ADMIN_IDS`
  (env, список через запятую; пусто — никто). Остальным — спокойный отказ без
  раскрытия причин и списка админов.
- `code`: `^[a-z][a-z0-9_]{1,31}$`, не меняется после создания.
- `unlock_threshold`: положительное целое, уникальное по каталогу.
- Имя 1–64, описание 1–160 (границы колонок БД).
- PNG: сигнатура, размер ≤ 1 MiB (проверяется и file_size из Telegram, и фактические
  байты), разрешение 256–1024 px по обеим осям, alpha-канал сохранён
  (color type 4/6 или palette+tRNS). Парсер PNG собственный, без новых зависимостей:
  читаются сигнатура, IHDR и список чанков; CRC не проверяется.

## Идемпотентность и конфликты

- Повторная доставка того же сообщения: если маскот с таким `code` существует
  с идентичными именем, описанием, порогом и байтами картинки — спокойный
  ответ «уже добавлен», без изменений и без дубликата.
- Существующий `code` с другими данными — отказ: «не перезаписывается».
- Занятый порог другим маскотом — отказ с подсказкой выбрать другой.
- Уникальные ограничения БД страхуют гонки; конфликт маппится в отказ.

## Ответы бота и логи

Все тексты спокойные, без давления, объясняют, что исправить. Успех —
подтверждение с параметрами и превью (эхо документа по file_id, текст —
caption). Логи: только событие `add_mascot` и исход (`created`/`already`/
`refused`/`invalid_png`/`download_failed`/`code_taken`/`threshold_taken`);
без текста команды, Telegram ID, file_id и байтов изображения.

## Приёмка

1. Валидная команда создаёт ровно одну запись каталога (`starter=false`,
   `active=true`, `asset_path=/api/v1/mascots/{code}/image`), отвечает
   подтверждением с превью; маскот виден в `GET /api/v1/mascots` и в
   `GET /api/v1/mascots/{code}/image` (`image/png`).
2. Повторная доставка того же сообщения не создаёт дубликат.
3. Ошибки формата (code/порог/имя/описание/не PNG/размер/разрешение/alpha)
   объясняют, что исправить, и не меняют данные.
4. Не-admin или не-личный чат — отказ, данных не меняется.
5. Новый порог автоматически участвует в PH-402 (разблокировки проверяются по
   каталогу при создании записи).
6. В логах нет текста команды, Telegram ID, file_id и содержимого изображения.
7. Полный прогон backend (включая DB-тесты) и `ruff` зелёные; фронтенд не
   меняется.
